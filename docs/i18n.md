# API internationalization

The API supports English (`en`) and Spanish (`es`). English is the neutral resource
language and request default. Host configures native `RequestLocalization` with
only `AcceptLanguageHeaderRequestCultureProvider`, before exception handling.
Standard parent-culture fallback maps `es-ES` to `es` and `en-US` to `en`.
Quality preferences are negotiated by ASP.NET Core. Missing or unsupported
headers use English. Query parameters and culture cookies cannot override this.
Culture is scoped to the request and never stored in a singleton or domain object.

## Resource ownership

`AddLocalization` uses `Resources` as its resource path. Each marker and its
resources belong to the adapter assembly owning the text:

| Owner | Marker | Resource directory |
| --- | --- | --- |
| Core HTTP | `CoreMessages` | `src/Alxarafe.AspNetCore/Resources` |
| Identity/Security | `SecurityMessages` | `src/Alxarafe.Security.AspNetCore/Resources` |

The neutral `.resx` contains English and `.es.resx` contains Spanish. Existing
explicit `.en.resx` module resources are retained. Native ResourceManager fallback
uses the neutral English resource when a more specific culture has no resource.
Host owns composition, not translation catalogs. Module resources ship with their
assemblies and do not depend on Host. Keys are namespaced by owner; physical
resource keys need not match Java's keys.

## Existing validation and ProblemDetails

Identity uses `LocalizedIdentityErrorDescriber`, the native Identity extension
point, with `IStringLocalizer<SecurityMessages>`. All framework describer methods
retain their framework codes and use complete Security phrases with native
parameters. Registration retains its existing ValidationProblemDetails structure
and `errors` keys such as `PasswordTooShort` and `DuplicateEmail`; only human title
and descriptions are localized. Its password policy, account semantics and
statuses remain unchanged. It remains a .NET-specific extension outside the
shared contract.

Future modules express structured validation failures independent of localization
and resolve their own complete parameterized resources at the HTTP boundary.
Core's existing transversal ArgumentException response retains its
semantics. Native HTTP status-page ProblemDetails titles are localized from Core;
unknown statuses use a generic resource phrase without exposing a missing key.
Technical extensions and type URLs remain stable. Internal exception messages
and operational logging are not translated.

Published v0.5.0 Health/AUTH/Users/Modules representations remain unchanged,
including closed code-only errors. Java's current closed errors do not acquire
ProblemDetail fields; cross-backend equivalence concerns shared semantics and
language negotiation, not identical implementation-specific error envelopes.
There is one OpenAPI structure. Its documentation is not localized in this task.

## Verification and extension

Run the existing Docker-only authority:

```bash
ERBAS_CONTRACT_DIR=/absolute/path/to/clean-v0.5.0-checkout ./bin/check
```

HTTP tests cover explicit English/Spanish, no header, unsupported French,
regional variants, quality preferences, ignored query/cookie selectors, request
isolation, Security-owned validation phrases, parameter interpolation and stable
codes/property sets. Existing domain, persistence and authorization tests remain.
The Core Bruno collection includes Spanish Identity validation alongside full
shared conformance. HTTP tests retain regional/default/fallback and parametrization
coverage, including native generic ProblemDetails through test-only probes.

A future Contact HTTP adapter should own its marker, resources, semantic errors
and validation mapping through the same native APIs. Do not add its texts to Host
or Core, wrap `IStringLocalizer`, concatenate translated fragments, or translate
technical identifiers. Stored user content, persistent language preferences,
translation databases, dynamic resource discovery and CONTACT-002 are not included.
